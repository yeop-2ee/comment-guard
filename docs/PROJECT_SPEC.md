## 0. 한 줄 요약

한국어 댓글을 **정상 / 공격적 / 혐오** 3단계로 분류하고 0~100점 **심각도 점수**를 매기는 API입니다. 이 점수로 두 가지 기능을 제공합니다.

1. **필터링:** 악플을 보기 싫은 사용자를 위해 민감도에 따라 댓글을 숨기거나 흐리게 처리
2. **증거 정리 리포트:** 악플 피해자가 신고나 고소를 준비할 때, 직접 모은 댓글을 심각도 순으로 정리하고 무결성 해시와 함께 내보내기

## 1. 서비스 개요

### 1.1 사용자와 목적

| 사용자 | 상황 | 원하는 것 | 제공 기능 |
|---|---|---|---|
| **A. 일반 열람자** | 뉴스·커뮤니티 댓글에 악플이 섞여 있어 보기 불편함 | 악플을 안 보고 싶음 (기준은 사람마다 다름) | 민감도별 필터링 (`/v1/filter`) |
| **B. 악플 피해 당사자** | 자신을 향한 악플이 반복적으로 달림 | 신고·고소 준비를 위해 악플을 체계적으로 정리하고 싶음 | 증거 정리 리포트 (`/v1/evidence/report`) |
| **공통 / 개발자** | 다른 서비스에 붙여 쓰고 싶음 | 댓글 1건 또는 여러 건의 판정 결과 | 분류 API (`/v1/classify`) |

### 1.2 입력과 출력 요약

- **입력:** 한국어 댓글 텍스트 (1건 또는 최대 100건). 리포트 기능은 URL, 작성 시각, 작성자 표시명 같은 메타데이터를 선택적으로 함께 받습니다.
- **출력:**
  - 판정 라벨(`none` / `offensive` / `hate`)과 클래스별 확률
  - 심각도 점수(0~100)와 등급(일반 / 주의 / 심각)
  - 편향 표시(성별 편향 포함 여부, 편향 유형)
  - 기능별 결과: 필터 처리 방식(보이기 / 흐리게 / 숨기기) 또는 리포트(JSON, CSV)

### 1.3 범위에 포함하지 않는 것

명시적으로 하지 않는 일입니다. README의 한계 항목에도 같은 내용을 적습니다.

- **법률 판단을 하지 않습니다.** 모욕죄나 명예훼손 해당 여부를 판정하지 않습니다. 리포트는 "정리 보조 자료"일 뿐입니다.
- **크롤링을 하지 않습니다.** 플랫폼에서 댓글을 자동 수집하지 않습니다. 사용자가 직접 확보한 댓글만 입력으로 받습니다. 플랫폼 약관 위반과 개인정보 수집 문제를 피하기 위해서입니다.
- **작성자 신원을 추적하지 않습니다.** IP나 실명 추적은 수사기관의 영역입니다.
- **원본 증거를 대체하지 않습니다.** 스크린샷이나 화면 녹화 같은 원본 증거는 사용자가 직접 보관해야 합니다. 서비스는 이미지를 받지 않고, 사용자가 원하면 스크린샷 파일의 해시값만 기록합니다.

## 2. 기능 명세

### 2.1 심각도 점수와 등급 (모든 기능의 공통 기반)

모델이 출력한 클래스 확률 `P(none)`, `P(offensive)`, `P(hate)`로 계산합니다.

```
severity_score = round(100 × (P(hate) + 0.5 × P(offensive)))   # 0~100 정수
```

| 등급 | 점수 범위 (기본값) | 의미 |
|---|---|---|
| `일반` (normal) | 0 ~ 29 | 문제 표현이 거의 없음 |
| `주의` (caution) | 30 ~ 59 | 공격적·무례한 표현 가능성 |
| `심각` (severe) | 60 ~ 100 | 혐오 표현 가능성이 높음 |

- **기준값을 정하는 방법:** 30/60은 시작값입니다. 최종 기준값은 **학습 데이터 안에서 떼어낸 검증 데이터(valid)** 로만 조정하고, 최종 평가 데이터(dev)는 절대 쓰지 않습니다(평가 데이터로 기준을 정하면 누수).
- **조정 규칙 (M2에서 확정, 2026-11-09):** `caution < severe`인 정수 조합(5~95)을 모두 시험해서 아래 순서로 비교합니다.
  1. medium 정상 오차단율 ≤ 15% (5.2장 목표)
  2. medium 혐오 차단율 ≥ 60% (5.2장 목표)
  3. 등급과 정답 라벨(normal↔none, caution↔offensive, severe↔hate)의 macro-F1이 가장 높음
  4. medium 혐오 차단율이 가장 높음
  - medium에서 정상 오차단율은 `caution` 기준값만, 혐오 차단율은 `severe` 기준값만으로 정해집니다. 그래서 혐오 차단율만 최대로 하면 `severe = caution + 1`이 되어 주의 등급이 사라집니다. 3번 조건은 이 퇴화를 막기 위한 것입니다.
  - 1번을 만족하는 조합이 없으면 정상 오차단율이 가장 낮은 조합을 고르고, 목표 미달을 기록합니다.
  - 시작값 30/60은 valid에서 정상 댓글의 약 65%를 가려서 쓸 수 없었습니다. 공식에 `0.5 × P(offensive)`가 들어가서 정상 댓글의 점수도 30을 쉽게 넘기 때문입니다.
- 기준값은 `configs/severity.yaml`에 저장하고, 모델 버전과 함께 기록합니다.

### 2.2 기능 F1 — 분류 API

`POST /v1/classify`

요청:
```json
{
  "texts": ["댓글1", "댓글2"]
}
```

응답:
```json
{
  "model_version": "m1-20261115-a1b2c3d",
  "results": [
    {
      "index": 0,
      "label": "offensive",
      "probs": {"none": 0.21, "offensive": 0.64, "hate": 0.15},
      "severity_score": 47,
      "grade": "caution",
      "bias": {"type": "none", "contain_gender_bias": false}
    }
  ]
}
```

입력 규칙:

| 조건 | 처리 |
|---|---|
| `texts`가 없거나 빈 배열 | 422 + 오류 메시지 |
| 배열 길이 > 100 | 422 |
| 공백만 있는 문자열 | 422 (어느 항목이 문제인지 index 포함) |
| 1,000자 초과 | 422 (임의로 자르지 않음, 결과 왜곡 방지) |
| 이모지, 특수문자, 영어 섞임 | 정상 처리 |

### 2.3 기능 F2 — 필터링 (사용자 A)

`POST /v1/filter`

요청:
```json
{
  "sensitivity": "medium",
  "comments": [
    {"id": "c1", "text": "댓글 내용"},
    {"id": "c2", "text": "댓글 내용"}
  ]
}
```

민감도별 처리 규칙:

| 민감도 | 일반 | 주의 | 심각 | 대상 사용자 |
|---|---|---|---|---|
| `low` | 보이기 | 보이기 | 숨기기 | 심한 것만 걸러내고 싶음 |
| `medium` (기본) | 보이기 | 흐리게 | 숨기기 | 일반적인 사용 |
| `high` | 보이기 | 숨기기 | 숨기기 | 무례한 표현도 보기 싫음 |

응답:
```json
{
  "model_version": "m1-20261115-a1b2c3d",
  "sensitivity": "medium",
  "results": [
    {"id": "c1", "action": "show", "grade": "normal", "severity_score": 8},
    {"id": "c2", "action": "blur", "grade": "caution", "severity_score": 41}
  ],
  "summary": {"show": 1, "blur": 1, "hide": 0}
}
```

설계 원칙:
- **"삭제"가 아니라 "숨김"입니다.** 오판 가능성이 있으므로 클라이언트에서 사용자가 펼쳐볼 수 있게 합니다. 응답에는 action만 주고, 원문은 클라이언트가 가지고 있습니다.
- 잘못된 `sensitivity` 값은 422로 처리합니다.

### 2.4 기능 F3 — 증거 정리 리포트 (사용자 B)

`POST /v1/evidence/report` (쿼리 `?format=json|csv`, 기본 json)

요청:
```json
{
  "case_title": "2026년 11월 ○○ 게시판 악플 정리",
  "items": [
    {
      "text": "댓글 원문",
      "url": "https://example.com/post/123#comment-456",
      "posted_at": "2026-11-01T21:14:00+09:00",
      "author_handle": "닉네임123",
      "captured_at": "2026-11-02T09:00:00+09:00",
      "screenshot_sha256": "선택: 사용자가 보관 중인 캡처 파일의 SHA-256"
    }
  ]
}
```

- `text`만 필수이고 나머지는 선택입니다. 빠진 항목은 리포트에서 경고로 알려줍니다.
- `items`는 최대 500건입니다.

리포트에 포함되는 내용:

1. **헤더:** `report_id`(UUID), `case_title`, 생성 시각(KST와 UTC), `model_version`, 심각도 기준값
2. **요약**
   - 등급별 건수 (심각 n건 / 주의 n건 / 일반 n건)
   - 기간: 가장 이른 `posted_at` ~ 가장 늦은 `posted_at`
   - 작성자별 건수와 최고 심각도. 반복 작성자를 파악하기 위한 용도이며, 사용자가 입력한 표시명만 그대로 씁니다.
3. **항목 목록 (심각도 내림차순 정렬)**
   - 순번, 원문, 등급, 점수, 클래스 확률, 편향 표시
   - URL, 작성 시각, 작성자 표시명, 캡처 시각
   - `text_sha256`: 원문 UTF-8 바이트의 SHA-256. 나중에 원문이 바뀌지 않았음을 확인하는 용도입니다.
   - `missing_fields`: 예) `["url", "posted_at"]`
4. **리포트 무결성:** `report_sha256`. 항목 목록을 키 정렬한 JSON으로 직렬화(canonical JSON)한 뒤 SHA-256을 계산합니다.
5. **증거 보강 체크리스트:** 고정 문구이며 입력 상태에 따라 체크 표시를 합니다.
   - [ ] 브라우저 주소창(URL)이 보이게 원본 화면을 캡처했는지
   - [ ] 작성자 ID/닉네임과 작성 일시가 함께 보이는지
   - [ ] 앞뒤 맥락(원글, 다른 댓글)까지 보존했는지
   - [ ] 화면 녹화로 해당 글을 찾아 들어가는 과정을 남겼는지
   - [ ] 원본 파일을 편집하지 않고 따로 보관했는지
6. **고지 문구 (필수, 삭제 금지):**
   > 이 리포트는 기계학습 모델의 자동 판정 결과를 정리한 참고 자료이며 법률 자문이 아닙니다. 모욕·명예훼손 등의 해당 여부는 피해자를 알아볼 수 있는지(특정성), 공개된 장소인지(공연성), 사실 적시 여부 같은 법적 요건에 따라 달라지며, 이 모델은 이를 판단하지 않습니다. 실제 신고·고소 시에는 원본 캡처와 URL 등 원 증거를 함께 제출하고, 필요하면 법률 전문가와 상담하세요. 온라인 신고 창구로 경찰청 사이버범죄 신고시스템(ECRM)이 있으며, 온라인 접수 후 경찰서 방문 진술이 필요할 수 있습니다.

CSV 형식:
- 항목 목록만 한 행에 1건씩, UTF-8 BOM을 포함합니다(엑셀에서 한글이 깨지지 않게).
- 헤더와 요약은 `#`으로 시작하는 주석 행으로 맨 위에 넣습니다.

저장 정책:
- **기본은 저장하지 않습니다.** 리포트는 응답으로만 반환하고, 서버와 클라우드 로그에 원문을 남기지 않습니다.
- 로그에는 `request_id`, 건수, 등급별 건수, 처리 시간, `model_version`, `report_sha256`만 남깁니다.

### 2.6 웹 화면 (`GET /`, 2026-11-09 추가)

API를 직접 호출하지 않아도 쓸 수 있는 화면을 같은 서버에서 제공합니다. `src/commentguard/static/index.html` 파일 하나이고, 외부 CDN이나 라이브러리를 쓰지 않습니다.

| 탭 | 대상 | 기능 |
|---|---|---|
| 댓글 필터 | 사용자 A | 댓글을 한 줄에 하나씩 붙여넣고 민감도를 고르면, 실제 댓글 목록처럼 보이기 / 흐리게 / 숨기기로 보여줌. 숨긴 댓글은 눌러서 펼칠 수 있음(삭제가 아니라 숨김) |
| 증거 리포트 | 사용자 B | 댓글과 선택 메타데이터(URL, 작성 시각, 작성자 표시명)를 입력하면 심각도 순 리포트, 요약, 경고, 체크리스트, 고지 문구를 보여주고 JSON·CSV로 내려받음 |
| 판정 상세 | 개발자·공통 | 클래스별 확률, 심각도 점수와 등급 기준선의 위치, 편향 표시, 확률과 등급이 엇갈리는 이유를 보여줌 |

- 화면은 API(`/v1/*`)만 호출합니다. 판정 로직이나 기준값을 화면에 따로 두지 않습니다.
- 밝은 테마로 고정합니다(OS 다크 모드와 무관). 색은 판정 등급(일반·주의·심각)에만 씁니다.
- 입력은 브라우저 밖으로는 이 서버에만 전송되고 저장되지 않습니다(D5). 화면에도 이 사실을 표시합니다.
- 작성 시각 입력은 한국 시간(+09:00)으로 보냅니다. API는 시간대가 있는 값만 받기 때문입니다.
- 배포하면 화면도 Vercel 프로덕션 도메인에서 그대로 열립니다. 화면과 API가 같은 주소라서 따로 설정할 것이 없습니다.
- 과제 평가 기준상 화면 디자인은 배점이 없습니다. 서비스 목적(필터링, 증거 정리)을 실제로 써볼 수 있게 하는 용도입니다.

### 3.2 데이터 구성

- 한국 연예 뉴스 댓글에 사람이 라벨을 붙인 데이터이며, 라벨이 있는 데이터는 총 8,367건입니다.
- 파일과 컬럼은 아래와 같습니다. M1에서 원본 저장소 커밋 `f8d05dce2b22007bb149e5139c0060c68ad8f94b`(2020-07-18)의 파일로 확인했습니다.

| 파일 | 건수 | 용도 |
|---|---|---|
| `labeled/train.tsv` | 7,896 | 학습 + 검증 분할 |
| `labeled/dev.tsv` | 471 | **최종 평가 전용** |
| `test.no_label.tsv` | 974 | 정답 없음(`comments` 컬럼만). 클라우드 스모크 테스트 입력으로만 사용 |

| 컬럼 | 값 | 이 프로젝트에서의 역할 |
|---|---|---|
| `comments` | 댓글 원문 | **입력** |
| `hate` | `hate` / `offensive` / `none` | **주 정답** (3클래스 분류) |
| `bias` | `gender` / `others` / `none` | 보조 정답 (편향 유형) |
| `contain_gender_bias` | `True` / `False` | 보조 정답 (성별 편향 여부) |

확인한 사실 (M1):
- 댓글에 큰따옴표가 들어간 행이 있어서 TSV를 **따옴표 처리 없이**(`quoting=QUOTE_NONE`) 읽습니다.
- `contain_gender_bias == (bias == "gender")`가 train과 dev 모든 행에서 성립합니다. 그래서 성별 편향 여부는 `bias` 예측에서 도출합니다(4.1장). `validate()`가 이 관계를 매번 다시 검사하고, 어긋나는 행 수를 기록합니다.
- 댓글 길이는 4~137자(평균 약 39자)입니다.

### 3.3 데이터 한 건의 의미와 단위

- **한 건 = 연예 뉴스 기사에 달린 댓글 1개**와, 그 댓글에 사람이 붙인 라벨입니다.
- 입력은 텍스트라서 물리 단위가 없습니다. 출력 확률은 0~1, 심각도 점수는 0~100 정수(단위 없음, 점)입니다.

### 3.4 잘못된 값 처리 기준

`src/commentguard/data.py`의 `validate()`에서 처리하고, 처리 결과를 `runs/<run_id>/data_report.json`에 숫자로 남깁니다.

| 검사 | 처리 |
|---|---|
| 댓글이 비었거나 공백만 있음 | 제거하고 건수 기록 |
| 라벨이 허용값 밖 | 제거하고 건수 기록 (있으면 원인 조사) |
| train 안의 완전 중복 (같은 텍스트, 같은 라벨) | 1건만 남김 |
| train 안에서 같은 텍스트인데 라벨이 다름 | 제거하고 건수와 예시 개수 기록 |
| **train과 dev에 같은 텍스트가 있음** | **train에서 제거** (평가 누수 방지) |
| 유니코드 정규화 | 학습과 서빙 모두 NFC 정규화 + 앞뒤 공백 제거 + 연속 공백 하나로 줄이기. 이모지와 특수문자는 유지 |
| `contain_gender_bias`와 `bias`가 어긋남 | 제거하고 건수 기록 (현재 0건) |

- 중복과 train/dev 겹침 검사는 **정규화한 텍스트 기준**으로 합니다.
- 가공 결과는 `data/processed/{train_fit,valid,eval}.tsv`(UTF-8, 따옴표 처리 없음)로 저장합니다. Git에서 차이를 볼 수 있도록 바이너리 형식 대신 TSV를 씁니다.

> **같은 전처리 함수를 학습과 서빙에서 공유해야 합니다** (`src/commentguard/text.py`의 `normalize()`). 학습할 때와 서빙할 때 전처리가 다르면 성능이 조용히 떨어집니다.

### 3.5 학습/검증/평가 분할 기준

| 구분 | 출처 | 용도 | 나눈 기준 |
|---|---|---|---|
| `train_fit` | train.tsv의 90% | 모델 학습 | `hate` 라벨 비율을 유지하는 층화 분할, `random_state=42` |
| `valid` | train.tsv의 10% | 하이퍼파라미터, 심각도 기준값 조정 | 위와 같음 |
| `eval` | dev.tsv 전체 | **최종 평가만** | 데이터 제작자가 나눈 공식 분할을 그대로 사용 |

- 전처리 기준(TF-IDF 어휘 사전, 기준값 등)은 `train_fit`(필요하면 `valid`)으로만 정합니다.
- 최종 모델은 하이퍼파라미터를 정한 뒤 `train_fit + valid`로 다시 학습할 수 있습니다. 이 경우에도 `eval`은 쓰지 않습니다.

### 3.6 누수 방지 체크리스트

- [ ] 입력은 `comments` 하나뿐인지 (편향 라벨을 입력에 넣지 않았는지)
- [ ] `eval`이 학습, 어휘 사전 구축, 기준값 조정 어디에도 쓰이지 않았는지
- [ ] train과 dev의 중복 텍스트를 제거했는지
- [ ] 클래스 가중치나 정규화 통계를 `train_fit` 기준으로 계산했는지

### 3.7 데이터 확보 방법 (README에 그대로 들어갈 내용)

- `scripts/download_data.sh`로 GitHub 원본에서 받습니다.
- 받은 뒤 `data/raw/MANIFEST.sha256`과 대조해 해시가 다르면 **중단**합니다.
- 원본·가공 데이터는 저장소에 포함합니다(D3). 다운로드 스크립트는 재확보와 해시 검증용으로 함께 둡니다.

## 4. 모델

### 4.1 모델 구성

| ID | 모델 | 역할 | 필수 여부 |
|---|---|---|---|
| `B0` | 최빈값 분류기 (`DummyClassifier(strategy="most_frequent")`) | 단순 기준 | 필수 |
| `M1` | 글자 n-gram TF-IDF + 로지스틱 회귀 | **주 서비스 모델** | 필수 |
| `M1-bias` | M1과 같은 특징 + 로지스틱 회귀 (`bias` 3클래스). `contain_gender_bias`는 `bias == "gender"`로 도출 (3.2장 확인 사실) | 편향 표시 | 필수 |
| `M2` | KcELECTRA-base 미세조정 | 사전학습 모델 비교 | **필수** (D2 결정: 본 과제로 승격) |

### 4.2 M1 상세

- 특징: `TfidfVectorizer(analyzer="char_wb", ngram_range=(2, 5), min_df=2, sublinear_tf=True, max_features=200_000)`
  - 한국어 댓글은 띄어쓰기가 불규칙하고 변형 욕설이 많아서, 형태소보다 **글자 n-gram**이 유리하고 외부 의존성도 없습니다.
- 분류기: `LogisticRegression(class_weight="balanced", max_iter=2000)`
- 조정할 하이퍼파라미터: `C ∈ {0.25, 0.5, 1, 2, 4}`. `valid`의 macro-F1로 선택합니다.
- 저장: `joblib`으로 저장하고, 산출물 크기를 기록합니다(수 MB~수십 MB 예상).
- 최종 모델은 `train_fit`으로 학습한 모델을 그대로 씁니다(`train_fit + valid`로 다시 학습하지 않음). 기준값을 valid 확률로 조정했기 때문에, 다시 학습하면 확률 분포가 바뀌어 기준값과 맞지 않게 됩니다.
- B0(`hate`, `bias` 각각의 최빈값 분류기)도 `train_fit`으로 학습해서 `models/<version>/b0.joblib`에 함께 저장합니다.

### 4.3 M2 상세

- 기반 모델: `beomi/KcELECTRA-base`. 한국어 댓글로 사전학습된 모델이며 MIT 라이선스입니다.
- **버전 고정:** `from_pretrained(..., revision="<커밋 해시>")`로 고정하고 해시를 모델 카드에 기록합니다.
  - 고정 리비전: `681201a097b8120e6dd2a2e63a3e13d338736f88` (2024-05-23, main). 저장소 이력상 `5deca41`(2023-04-03)에서 main의 가중치와 토크나이저가 **v2023 + byte-level BPE**로 바뀌었고, 모델 카드 본문은 이전 WordPiece 설명이 그대로 남아 있습니다. 가중치와 `tokenizer.json`은 같은 리비전이라 서로 맞습니다(vocab 30,000).
  - 이 리비전의 `tokenizer.json`에는 post-processor가 없어 `[CLS]`/`[SEP]`이 자동으로 붙지 않습니다. `m2.encode()`에서 직접 붙입니다(`tests/test_m2.py`).
- 구조: ELECTRA 인코더 + `[CLS]` 위치에 분류 머리 2개(hate 3클래스, bias 3클래스). loss = CE(hate) + 0.5 × CE(bias), 클래스 가중치는 `train_fit` 기준 balanced. 학습률 {2e-5, 5e-5} × 최대 5에폭, valid hate macro-F1로 조기 종료·선택(`configs/train.yaml`의 `m2`).
- 산출물: `models/m2-<날짜>-<커밋>/`(가중치 safetensors, 설정, 토크나이저, 모델 카드). 서빙 시 허브에 접속하지 않고 이 폴더만으로 로드합니다.
- 학습은 로컬(Apple Silicon MPS) 또는 Colab GPU에서 하고, 서빙은 CPU로 합니다.
- 하이퍼파라미터(학습률, 에폭)와 조기 종료는 `valid`로만 정합니다. 심각도 기준값도 모델별로 `valid`에서 다시 조정합니다.
- 학습용 의존성(torch, transformers)은 `requirements-m2.txt`로 분리해서 서빙 함수를 작게 유지합니다.
- **서빙 모델 선택:** M1과 M2를 같은 eval로 비교하고(macro-F1, 신뢰구간, 필터 지표, CPU 지연시간, 메모리, 모델 파일 크기), 그 결과를 근거로 Vercel에 올릴 모델을 정해 `EVALUATION.md`에 이유를 적습니다. 선택 전까지 배포 기준 모델은 M1입니다.
- 고려사항: 가중치가 약 500MB라 함수가 새로 시작할 때 모델을 받는 시간(cold start)이 길어지고, PyTorch는 Vercel 함수 크기 한도(500MB)를 넘습니다. 서빙은 ONNX로 변환해 실행하는 방안을 비교합니다. 이 차이를 비교 결과로 기록하면 클라우드 구성 선택 이유가 됩니다.

### 4.4 모델 버전 규칙

```
<모델ID>-<YYYYMMDD>-<git 커밋 앞 7자리>
예: m1-20261115-a1b2c3d
```

모델 산출물 폴더 `models/<model_version>/`에 아래 파일을 둡니다.
- `model.joblib`(또는 M2 가중치)

## 5. 평가

### 5.1 모델 품질 평가

| 항목 | 내용 |
|---|---|
| 평가 데이터 | `eval` (dev.tsv, 471건). 학습과 조정에 쓰지 않은 공식 분할 |
| 주 지표 | **macro-F1** (3클래스). 클래스 불균형 때문에 정확도는 보조로만 사용 |
| 보조 지표 | 클래스별 정밀도·재현율·F1, 정확도, 혼동행렬 |
| 비교 대상 | B0(최빈값) vs M1 (vs M2). 같은 eval 데이터, 같은 계산 코드 |
| 불확실성 | 평가 건수가 적어서, macro-F1에 **부트스트랩 95% 신뢰구간**(1,000회 재표본, seed 고정)을 함께 보고. 같은 재표본으로 M1−B0 차이의 구간도 계산. 차단율 같은 비율 지표는 Wilson 95% 구간 |
| 편향 모델 | `bias` macro-F1, `contain_gender_bias` F1을 따로 보고 |

### 5.2 서비스 목적 기준 평가 (심각도와 필터)

모델 지표만으로는 "서비스가 목적에 맞는지"를 보여주기 어려워서 아래 지표를 추가합니다. eval 데이터로 계산합니다.

| 지표 | 정의 | 의미 |
|---|---|---|
| 민감도별 혐오 차단율 | 정답이 `hate`인 댓글 중 해당 민감도에서 `hide`된 비율 | 악플을 얼마나 잘 걸러내는지 |
| 민감도별 정상 오차단율 | 정답이 `none`인 댓글 중 `hide`되거나 `blur`된 비율 | 멀쩡한 댓글을 얼마나 잘못 가리는지 |
| 등급 순서 일치도 | 정답(none < offensive < hate)과 심각도 점수의 스피어만 상관 | 점수가 실제 심각한 순서를 반영하는지 |

**목적 적합 판단 기준 (사전에 정하고 결과와 비교):**
- M1의 macro-F1이 B0보다 확실히 높을 것 (신뢰구간이 겹치지 않음)
- `medium` 민감도에서 정상 오차단율 ≤ 15%, 혐오 차단율 ≥ 60%
- 기준을 못 맞추면 그대로 보고하고 원인을 분석합니다. **성능 자체는 배점이 없으므로 숫자를 억지로 맞추지 않습니다.**

### 5.4 잘못된 결과 1건 분석

- eval에서 **틀린 예측 1건**을 골라 분석합니다. 놓친 혐오(hate인데 none으로 예측)를 우선 고릅니다.
- 분석 항목: 원문(욕설이나 실명은 일부 `*` 처리), 정답, 예측, 확률, 영향을 많이 준 n-gram(로지스틱 회귀 계수 상위), 원인 추정(반어법, 맥락 의존, 변형 표기, 라벨 애매함 등), 개선 아이디어

### 5.6 행동 검사 세트 (2026-11-10 추가)

eval은 실제 분포의 평균 성능을 보여주지만, 서비스에서 문제가 된 특정 유형(신조어 칭찬을 악플로 판정 등)은 eval에 거의 없어서 따로 잽니다. 과제 안내의 "사전학습 모델은 대표 입력과 기대 결과로 평가"에도 해당합니다.

- 파일: `data/probes/behavior.tsv` (직접 만든 가짜 예시, 컬럼 `category`, `expected`, `text`)
- `expected`: `ok`(보여야 함) 또는 `toxic`(가려야 함). medium 민감도에서 `ok`는 보이기, `toxic`은 흐리게 또는 숨기기여야 정답입니다.
- 유형(각 6문장): '개' 강조 칭찬 / '개' 비하 / 초성 칭찬 / 초성 욕설 / 이모지 칭찬 / 정상 비판 / 일반 욕설. 짝을 이루는 유형(칭찬 vs 비하)을 넣어서, 표면 글자가 아니라 뜻을 구분하는지 봅니다.
- **모델 결과를 보기 전에 문장을 모두 작성하고 SHA-256을 `data/probes/MANIFEST.sha256`에 고정합니다.** 결과를 본 뒤 문장을 바꾸지 않습니다.
- **학습, 어휘 사전, 하이퍼파라미터, 기준값 조정에 쓰지 않습니다.** 측정에만 씁니다.
- 지표: 유형별 정답률, `ok` 유형의 오차단율, `toxic` 유형의 놓침률. `python -m commentguard.probe` → `runs/<id>-probe/probe_metrics.json`
- 한계: 42문장이라 통계적 결론이 아니라 유형별 경향을 보는 용도입니다. 작성자 한 명이 만든 문장이라 표현이 편향될 수 있습니다.

### 5.5 측정하지 못한 부분과 한계 (README에 그대로)

- 연예 뉴스 댓글에 한정되어 있어서, 게임·정치·SNS 등 다른 영역에서의 성능은 측정하지 않았습니다.
- 데이터 수집 시점 이후의 신조어나 변형 욕설에는 약할 수 있습니다.
- 혐오와 공격적 표현의 경계는 라벨링한 사람마다 다를 수 있습니다(라벨 자체의 불확실성).

## 6. 시스템 구성과 클라우드

### 6.1 구성도 (D1 결정: Vercel, 2026-11-09)

```
[브라우저 / curl / 스모크 스크립트]  ── HTTPS JSON
        │
        ▼
[Vercel 프로덕션 도메인] ─▶ [현재 배포: Python 함수 (FastAPI), 리전 icn1]
                             ├─ 시작 시 로드 ─▶ [Vercel Blob (비공개): models/<version>/]
                             └─ 요청 로그(원문 제외) ─▶ [Vercel 런타임 로그]

[로컬] 데이터 → 검증 → 학습 → 평가 → 테스트 → 모델 업로드 → 배포 → /health 확인 → 프로덕션 승격 → 스모크
        └─ 모든 단계 기록 ──▶ runs/<run_id>/run.json (저장소에 커밋)
```

### 6.2 구성과 선택 이유 (Vercel)

| 항목 | 선택 | 이유 |
|---|---|---|
| 실행 | **Vercel Functions (Python 런타임)** + FastAPI | 요청이 있을 때만 함수가 실행되고 요청이 없으면 비용이 없음. 짧은 요청-응답 API라 상시 서버가 필요 없음. 같은 FastAPI 앱을 로컬 `uvicorn`과 Vercel에서 그대로 실행하고, 화면(`GET /`)과 API를 같은 주소로 제공 |
| 제외한 후보 | 상시 실행 서버(VM·컨테이너 서비스): 요청이 없어도 비용 발생. Edge 런타임: Python과 모델 라이브러리를 실행할 수 없음 | — |
| 진입점 | Vercel 프로덕션 도메인 (HTTPS) | 화면을 브라우저로 바로 열 수 있음. 남용은 입력 크기 제한(2.2장)과 Hobby 플랜 한도(초과 시 과금 없이 중지)로 막음. 프로덕션 외 배포 주소는 Deployment Protection(Vercel 로그인 필요)으로 막힘 |
| 버전·롤백 | 배포마다 새 배포(변경 불가)를 만들고, 그 배포의 `/health`가 통과해야 `vercel promote`로 프로덕션 도메인을 옮김 | 새 배포가 시작에 실패하면 승격하지 않아 이전 정상 배포가 계속 서비스함. 문제가 생기면 `vercel rollback`으로 되돌림 |
| 리전 | `icn1` (서울) | 사용자가 한국에 있음. 모델 저장소도 같은 리전에 둠 |
| 모델 저장 | Vercel Blob **비공개** 저장소 (버전별 경로 `models/<version>/`) | 코드와 모델을 분리해서 모델만 교체 가능. CLI 배포 업로드 한도(Hobby 100MB) 때문에 모델을 배포에 넣지 않음 |
| 로그 | Vercel 런타임 로그 (Hobby 1시간 보존) | 원문은 남기지 않음. 보존이 짧아서 스모크 직후 `vercel logs`로 받아 `runs/`에 저장 |
| 실행 설정 | 메모리 2GB(vCPU 1), 최대 실행 시간 60초 | M1 기준으로 충분. M2를 쓰면 다시 측정 |
| 인증 | 배포자는 `vercel login`(브라우저 인증). **장기 토큰을 만들지 않음** | 토큰 유출 위험 제거 |

### 6.3 서비스 시작 동작

1. 환경변수 `MODEL_URI`(예: `blob://models/m1-20261109-591d16d/`)를 읽습니다. 배포할 때 `vercel deploy --env MODEL_URI=...`로 배포마다 지정합니다.
2. 모델 파일과 `model_card.json`을 내려받아 로드합니다.
3. 실패하면 **명확한 오류 메시지를 로그에 남기고 시작을 중단합니다.** 조용히 빈 모델로 뜨지 않게 합니다. Vercel에서는 함수 시작이 실패해 요청이 500으로 끝납니다.
   - `MODEL_URI`가 없으면 로컬 `models/LATEST`를 씁니다(로컬 개발용). `blob://`로 시작하면 Blob 저장소에서, 아니면 로컬 경로에서 읽습니다.
   - 모델 파일은 joblib(pickle)이라 신뢰하는 본인 저장소에서만 읽습니다.
4. 성공하면 `/health`가 200을 반환합니다.

### 6.4 클라우드 실행 기록 (과제 "나" 항목)

`scripts/smoke_cloud.py`의 실행 결과를 `runs/<run_id>/cloud_smoke.json`에 남깁니다.
- 프로덕션 도메인, 배포 ID, 리전, `MODEL_URI`(저장소 ID는 가림)
- 케이스별 요청 본문(공개 데이터의 댓글만 사용), 응답 상태, 응답 본문, 지연시간
- 실행 시각, git 커밋, 성공/실패
- 스모크 직후 그 배포의 런타임 로그를 받아 같은 폴더에 저장하고, 로그에 댓글 원문이 없는지 확인합니다.

**파일 업로드가 아니라 실제 실행 결과로 증명해야 합니다.** 응답의 `model_version`과 배포 ID가 같이 남아야 합니다.

## 7. 실행 파이프라인과 실행 기록

### 7.1 단계와 명령

`Makefile`이 진입점입니다. 각 타깃은 `scripts/` 또는 `python -m commentguard.<모듈>`을 호출합니다.

| 순서 | 명령 | 하는 일 | 산출물 |
|---|---|---|---|
| 1 | `make setup` | 가상환경 생성, `requirements.txt` 설치 | `.venv/` (Git 제외) |
| 2 | `make data` | 다운로드 + 해시 검증 | `data/raw/` |
| 3 | `make validate` | 3.4장 검사 + 분할 | `data/processed/`, `data_report.json` |
| 4 | `make train` | B0, M1, M1-bias 학습 | `models/<version>/` |
| 5 | `make evaluate` | 5.1~5.2장 평가 | `runs/<id>/metrics.json`, 혼동행렬 이미지 |
| 6 | `make test` | pytest (5.3장) | 테스트 결과 |
| 7 | `make upload-model` | 모델을 Blob 저장소에 업로드 | `blob://models/<version>/` |
| 8 | `make deploy` | Vercel 배포, `/health` 확인 후 프로덕션 승격 | 배포 ID |
| 9 | `make smoke` | 클라우드 스모크 테스트 | `cloud_smoke.json` |
| 10 | `make cleanup` | 자원 정리 + 상태 재조회 | `cleanup_status.txt` |
| — | `make all-local` | 2~6 순서대로 | — |

### 7.2 실패 처리 규칙

- 모든 스크립트는 `set -euo pipefail`(bash)를 쓰거나, 실패 시 0이 아닌 종료 코드를 반환(Python)합니다. Make는 실패한 단계에서 멈춥니다.
- 해시 불일치, 검증 실패, 테스트 실패, 스모크 실패가 나면 **다음 단계로 진행하지 않습니다.** 예를 들어 `make test`가 실패하면 `deploy`를 막습니다.
- 실패한 실행도 기록을 남기되 `status: "failed"`로 표시해서, 정상 결과와 섞이지 않게 합니다.

### 7.3 실행 기록 형식

모든 단계는 `src/commentguard/runlog.py`의 공통 함수로 기록합니다.

`runs/<run_id>/run.json` (`run_id = YYYYMMDD-HHMMSS-<단계>`):
```json

  "step": "train",
  "started_at": "2026-11-15T14:23:01+09:00",
  "finished_at": "2026-11-15T14:24:10+09:00",
  "status": "success",
  "git_commit": "a1b2c3d4e5...",
  "git_dirty": false,
```

## 8. 오류 재현과 복구

### 8.1 재현할 오류 (주 시나리오): 잘못된 모델 경로

| 항목 | 내용 |
|---|---|
| 재현 방법 | 배포할 때 `MODEL_URI`를 존재하지 않는 버전 경로로 지정 (예: `blob://models/m1-20261109-WRONG/`) |
| 예상 증상 | 새 배포의 함수가 시작할 때 모델 경로를 찾지 못해 로드 실패 → 함수 시작 실패(500). 배포 스크립트의 새 배포 `/health` 확인이 실패해서 배포 명령이 0이 아닌 코드로 끝남. 승격하지 않아 프로덕션 도메인은 이전 정상 배포를 계속 서비스함 |
| 기록할 것 | 실패한 배포 명령, 오류 메시지 원문(저장소 ID 등 가림), 런타임 로그의 `model_load_failed`, 실패 시각, 영향(새 배포 미반영, 기존 서비스 영향 여부를 스모크로 확인) |
| 원인 조사 | `vercel logs`로 시작 로그 확인 → `vercel blob list`로 해당 경로가 없음을 확인 |
| 수정 | ① 배포 스크립트가 배포 전에 `MODEL_URI` 경로에 `model_card.json`과 모델 파일(`model.joblib`)이 있는지 미리 검사(재발 방지. 망가진 배포가 만들어지기 전에 막음), ② 올바른 경로로 재배포 |
| 재검증 | 실패했던 배포 명령을 올바른 값으로 다시 실행 → 성공 / 스모크 전체 재실행 → 통과 / 일부러 틀린 경로로 다시 시도 → 이번에는 배포 전 검사에서 막히고 새 배포가 만들어지지 않는지 확인 |
| 산출물 | `docs/INCIDENT.md` + `runs/<id>-incident-*/` (실패 기록은 `status: failed`로 분리) |

## 10. 권한, 비용, 자원 정리

### 10.1 권한

| 주체 | 권한 | 대상 | 이유 |
|---|---|---|---|
| 본인 계정 (배포자, `vercel login`) | 프로젝트 배포·승격·롤백, Blob 저장소 생성·업로드·삭제, 로그 조회 | 본인 Hobby 계정의 이 프로젝트와 저장소 | 배포와 정리 |
| 함수 (런타임) | Blob 저장소 읽기 (Vercel이 발급하는 단기 OIDC 토큰) | 이 프로젝트에 연결한 저장소만 | 모델 읽기만 |
| 호출자 | 없음 (공개) | 프로덕션 도메인만. 다른 배포 주소는 Vercel 로그인 필요 | 화면 공개 |

- **장기 토큰을 만들지 않습니다.** 로컬에서는 `vercel login`으로 인증하고, Blob 읽기·쓰기 토큰을 만들어 파일에 저장하지 않습니다.
- 프로젝트·저장소 이름은 `configs/deploy.env`(Git 제외)에 두고, 저장소에는 `configs/deploy.env.example`만 올립니다. 기록과 문서에서는 Blob 저장소 ID를 가립니다.
- 공용 자원이나 조직 보안 설정은 바꾸지 않습니다(과제 조건).

### 10.2 비용이 발생하는 자원과 제한 방법

| 자원 | 비용 요인 | 제한 방법 |
|---|---|---|
| Vercel Functions | 실행 시간(Active CPU), 메모리 시간, 호출 수 | Hobby(무료) 플랜 한도 안에서만 동작하고 초과하면 과금 없이 중지. 요청이 없으면 0. 최대 실행 시간 60초 |
| Vercel Blob | 저장 용량, 전송량, 작업 수 | Hobby 한도(저장 1GB, 전송 10GB/월). M1 수 MB 수준. 함수가 새로 시작할 때마다 모델을 한 번 받음. 정리 시 삭제 |
| 런타임 로그 | — | Hobby 1시간 보존, 추가 비용 없음 |
| 공통 | — | **Hobby 플랜으로 진행해 결제 수단을 등록하지 않음**(유료 플랜으로 올리지 않음) |

### 10.3 자원 정리

`scripts/cleanup.sh`:
1. Blob 저장소의 모델 삭제 후 저장소 삭제 (보관한다면 이유와 삭제 예정일 기록)
2. Vercel 프로젝트 삭제 (배포, 프로덕션 도메인 포함)
3. **정리 후 상태 재조회** 결과를 `runs/<id>-cleanup/cleanup_status.txt`에 저장
   - `vercel project ls`
   - `vercel blob list-stores`
   - 프로덕션 도메인에 요청해 더 이상 응답하지 않는지(404) 확인

남겨둔 자원이 있으면 `docs/COST_AND_CLEANUP.md`에 이유와 정리 계획을 적습니다.

## 11. 개인정보, 윤리, 법적 고려

### 11.1 저장소와 로그에 넣지 않는 것

- 비밀번호, API 키, 토큰(Vercel 토큰 포함), 결제 정보
- 사용자가 리포트 기능에 입력한 실제 댓글이나 작성자 정보 (테스트에는 공개 데이터와 직접 만든 가짜 예시만 사용)
- 클라우드 로그의 댓글 원문 (로깅 미들웨어에서 본문을 기록하지 않도록 구현하고 테스트로 확인)
- `.venv/`, `__pycache__/`, 임시 파일, 대용량 모델 가중치(M2)

### 11.2 데이터 자체의 민감성

- 학습 데이터에는 욕설, 혐오 표현, 연예인 실명이 포함되어 있습니다.
- README, 오류 분석, 캡처에서 예시를 보여줄 때는 실명과 심한 욕설 일부를 `*`로 가립니다.

### 11.3 기능별 윤리 원칙

- **필터링:** 오판으로 정상 댓글이 가려질 수 있으므로 삭제하지 않고 숨김 처리합니다. 사용자가 민감도를 고를 수 있게 합니다.
- **증거 리포트:**
  - 법률 판단이 아니라는 고지를 리포트에 항상 포함합니다(2.4장).
  - 모델이 "일반"으로 판정했다고 해서 피해가 없다는 뜻이 아님을 명시합니다. 맥락 의존적인 괴롭힘은 놓칠 수 있습니다.
  - 리포트를 쓴다고 원본 캡처, URL, 화면 녹화 같은 원 증거 보존이 필요 없어지는 게 아님을 체크리스트로 안내합니다.
  - 사용자가 입력한 작성자 표시명 외에 신원 정보를 수집하거나 추론하지 않습니다.
- **편향:** 학습 데이터 특성상 특정 집단 관련 표현에서 과잉·과소 탐지가 있을 수 있습니다. 편향 라벨별 성능 차이를 가능하면 함께 보고합니다.
